# 任務：線上更新架構導入

- **目標**：建立可維運的線上更新機制（檢查、下載、部署、回滾）以支援 F1T 專業版商業化。
- **負責人**：待指派
- **建立日期**：2025-10-03
- **關聯專案**：API-ONLY 模式調整、GUI/CLI 模組化維運

## 背景與動機
- API-ONLY 模式限制 GUI 直接呼叫 CLI，未來功能發布需有集中更新管道。
- F1T 商業化需要穩定的版本管理、補丁分發與企業級維護能力。
- 現有架構已具模組化 CLI、REST API 與 GUI 工作站，是導入線上更新的良好基礎。

## 核心目標
1. 在 `core/` 導入統一的版本管理元件（GUI/CLI/語言包）。
2. 擴充 `refactored_api.py` 以提供版本查詢、更新下載與更新歷程 API。
3. 建立 GUI 端自動檢查與用戶互動流程（通知、授權驗證、進度視覺化）。
4. 設計安全可回滾的更新部署流程（簽章驗證、備份、增量套件）。

## 範圍界定
- **包含**：版本管理、API 擴充、GUI 前端整合、更新套件格式、測試與回滾機制。
- **排除**：雲端部署與 CDN 設定細節、授權管理後端（僅定義介面）。

## 里程碑與階段
| 階段 | 內容 | 產出 |
|------|------|------|
| Phase 1 | 版本資訊管理與基本檢查 | `VersionManager` 原型、`/updates/check` API、GUI 通知 UI 草稿 |
| Phase 2 | 自動下載與簽章驗證 | 更新套件格式（ZIP + 摘要）、下載流程、驗證邏輯、失敗回報 |
| Phase 3 | 部署與回滾 | 備份策略、部署腳本、回滾機制、權限檢查 |
| Phase 4 | 進階功能 | 更新頻道（stable/beta）、授權驗證對接、遙測統計 |

## 測試計畫
- 單元測試：`VersionManager` 功能、API 參數驗證、簽章驗證流程。
- 整合測試：模擬下載與套件安裝，驗證備份與回滾。
- GUI 測試：更新流程對話框、通知、錯誤提示、多語系顯示。
- 壓力測試：模擬大量客戶同時檢查更新時的 API 負載。

## 成功判斷指標
- 使用者可於 GUI 內完成「檢查 → 下載 → 安裝 → 重啟」流程且記錄可追溯。
- 更新套件可被驗證簽章，失敗時仍可安全回滾至前一版本。
- API 日誌可追蹤更新請求、狀態與錯誤；跨語系提示正確顯示。

## 風險與緩解
- **更新檔損毀**：加入簽章與摘要驗證、保留最新兩個版本完整備份。
- **權限限制**：更新腳本需處理 Windows UAC 與檔案鎖定；提供手動安裝替代方案。
- **網路中斷**：支援斷點續傳或至少在失敗時自動重試並友善提示。
- **授權衝突**：先與授權系統定義介面與錯誤碼，再逐步啟用強制驗證。
